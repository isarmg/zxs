# 在封存副本上检查 exFAT

`helper check-exfat-copy /绝对路径/volume.img --sha256 完整的可信SHA256`

只接受已保存的单卷普通镜像，不接设备节点、整盘分区表、网页路径、附加参数或上传。授权的检查仅为 `fsck.exfat -n`。先以和 [FAT32 副本检查](fat32-copy-check.md) 相同的原文件、挂载、单链接、无符号链接、读取权限和 NOATIME 边界处理；最多 128 MiB。复制到新建的禁执行匿名内存文件，封死写入/增长/截短；从整份封存副本复核外部 SHA-256、EOF，再复核原位置。工具只能看见另一个只读的 `/image`，不与原文件共享可写视图。不判断原文件曾否挂载，也不保证它最新。

格式门只核[微软规范中的卷起点和边界](https://learn.microsoft.com/en-us/windows/win32/fileio/exfat-specification#31-main-and-backup-boot-sector-sub-regions)：引导标识、必须为零的区段、1.00 版、单 FAT 且以该 FAT 为当前表、扇区和簇大小范围、声明的卷长度恰与完整镜像相等。本命令接受 1–128 MiB；切出的卷可保留原分区偏移。其他格式、截短/尾随数据、双 FAT、标题已无法辨明、超出预算等均报未能检查，不判介质损坏。分配表、目录和校验和由上游检查器处理，不另写一套 fsck。

[Debian 13 amd64 发行配方](../packaging/debian13-amd64/README.md)使用 `exfatprogs 1.2.9-1+deb13u1`，独立策略文件为私有工具根下的 `exfat-check-v1`。固定八槽，与 FAT32 的策略文件不能互换。逐个核对受保护的原 ELF、完整摘要与安装位置。只把选定检查器、加载器、libc、只读副本投射进和 FAT32 相同的受限命名空间；无宿主目录、终端、网络或块设备，且检查器不能派生子进程。共用 30 秒时限、输出预算、真实 handoff 与整进程组回收；失败不改用宿主工具。CLI 可直接调用；[本机磁盘面板](disk-web.md)也可在终端用 `--exfat-copy` 预选同一份镜像，配对后预览并确认一次。普通配对不能授予检查权。

|helper 返回码|如何解读|
|---|---|
|0|收到原工具版本、沙箱完成回执和进程真实退出 0；只有预期的 clean 统计，无额外诊断，主引导扇区的 dirty/介质失败位也未设置。这是本次只读检查**未报告问题**，不是文件正文、备用引导区或整盘健康证明。|
|1|原工具报 4，且实际尾部明确报告非零未修复数、零修复和一致的目录/文件统计；只表示上游报告问题，不保证所有目录均已遍历。另一种单独标明的情况是原工具报 0、但封存卷的 dirty/介质失败位已置位，不能将这个卷当作无须注意。|
|2|检查未能确认：原工具报 4 但没有明确的问题统计，0 却伴额外诊断，8（操作错误）、16（用法错误）、任何其他退出、截断的输出、运行环境不合、超时、身份或摘要不符等。即使看见“clean”两个字，也不覆盖真实错误退出。|

根目录计入目录统计。只输出固定说明、标记与已解析数字，不传卷标、文件名或原始诊断；不尝试修复、重放或清除 dirty。1.2.9 在根遍历失败时也可能打印 clean，且只读模式通常不检查冗余引导区；这也是不用单一字符串判断的原因。[检查器的实际控制流](https://github.com/exfatprogs/exfatprogs/blob/1.2.9/fsck/fsck.c#L1634-L1735)、[Debian 此版补丁](https://sources.debian.org/patches/exfatprogs/1.2.9-1%2Bdeb13u1/)。

源码内有完整和不完整的输出案例，以及未来隔离 Debian 验收用的 clean/errors 镜像和独立 SHA 输入：`HELPER_TEST_EXFAT_{CLEAN,ERRORS}_IMAGE`、`HELPER_TEST_EXFAT_{CLEAN,ERRORS}_SHA256`。镜像由测试管理员独立准备，预期 clean 用干净空卷，errors 用稳定能得到末端未修复计数的副本。检查返回后对比原文件实体和修改时间，错摘要须拒绝。本次未构建、执行或读取实际镜像。

## 只修新建的工作副本

由非 root 操作者在本机前台运行，给出已保存单卷镜像的绝对路径、独立取得的完整 SHA-256 和一个**尚不存在**的输出目录。请输入刚显示的 `REPAIR-EXFAT-COPY` 挑战确认。输入不挂载、不可为设备或现用 loop 后端，输出不会覆盖同名文件或目录；操作也不会接管旧暂存。

```sh
/usr/bin/helper repair-exfat-copy /saved/volume.img --sha256 HEX --output /work/new-volume
```

确认后才保留原只读租约，同一遍完整读取比对摘要并另写一份。工具只看见新建普通文件 `/image`，不见输入、设备、宿主目录或终端。对新文件仅用包内 `fsck.exfat -p`。**即使是自动模式，也可能截短文件、改名或删除坏目录项。** 不启用 `-y`、`-b` 或 `-s`，不补救挂载或日志，也不对来源或原盘做修复。限定主引导仍可识别、原单 FAT 1.00 边界可核；失败不能证明原盘坏。[上游手册](https://manpages.debian.org/trixie/exfatprogs/fsck.exfat.8.en.html)和[固定版的自动决策表](https://github.com/exfatprogs/exfatprogs/blob/1.2.9/fsck/repair.c#L34-L64)说明细节。

只有原 `-p` 实际退出 0 或 1、确切终场成立、没有 stderr 与报告未修复项，才同步并关闭工作写 FD，再以原名重开同 inode。复查要求原 BPB 几何和卷识别字段不变（dirty 等状态位可变），重新算全文件 SHA/EOF，以另一个纯只读沙箱运行固定 `-n`，确切退出 0 且无额外诊断或 dirty/介质失败位，才用同父不可覆盖改名发布 `NEW_DIR/image.exfat`。这是本次元数据复查未报告问题，**不证明普通文件正文保全、备用引导区完整、可挂载或介质健康**。初次 `-p` 的状态不是正文完整或没有发生写入的证明。正面输出只给新文件摘要和固定结果，不回显上游诊断中的文件名。

工作路径使用流式读和本地新文件，不受上述只读内存快照的 128 MiB 限制。输出需要容纳完整镜像的空间与原有系统限额；两轮工具各有 10 分钟墙钟及最多 300 秒子进程 CPU，整份复制散列另受取消与实际 I/O 限制。中断、无空间、租约破坏、额外诊断、进程未能回收或复查失败，都不报发布成功；按本机预览保留工作目录与可能已改名但未确认的输出，不自动删除。普通本机配对面板仍只提供 exFAT 的旧只读检查，不发起这项修复。源码反例为静态用例，未实际运行、修复或接触设备。
