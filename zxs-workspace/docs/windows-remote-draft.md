# Windows：一个远程节点的本机工作文件（内部源码）

这不是已交付的编辑盘。下面先介绍不依赖驱动的原始编辑正文，再描述受独立签名验收门约束的 WinFsp、桌面和提交源码；无合格记录时不能挂载或提交。原先的固定 ZIP 只读视图和单节点另存均不因此获得写权限。

- **确定原件。** 选择记录 HTTPS 来源及信任策略、账号、容器 ID/原名/版本、分支、分支头和选中的原节点（包含长度和 SHA-256）。准备时仅持续持有已选私用 NTFS 父目录；确认前不创建文件、不重新请求数据。确认后在同一认证读取器重查所选详情，版本、名称或分支头已变就停止，绝不改选最新。只 GET 原节点。选择时还须明确这份本机工作文件的逻辑字节上限，至少容纳所选正文；这不是磁盘预留或配额保证。
- **保存正文。** 初始文件用无覆盖 FILE_CREATE 以独占的数据句柄创建在该父目录，只用新生成的内部名称；远端的 `CON` 等名称不会被用作 NTFS 文件名，也不会因本机选择改名。遵从系统对该 HTTPS URL 的实际来源区域和保存标记策略：需要标记时，先在这个文件写入、同步及核验 `Zone.Identifier`，再收正文。用相同的原句柄同步、读回全文、核实原名/文件 ID/权限、父目录和来源流。此标记不是查毒或运行许可。
- **编辑与停写。** 只对默认数据流提供有限长度的偏移读写和修改文件长度，未交付真实用户/内核/编辑器文件句柄。同步 HANDLE 上的定位、读写、改长与审阅串行；使用 [FilePositionInformation / FileEndOfFileInformation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntsetinformationfile)，不使用会暴露旧介质数据的 valid-data-length 特权操作。追加在同一把锁内采用当前 EOF，受限的延迟写只覆盖仍在当前长度内的部分，不会在刚缩短后把文件重新撑大。依据 [WinFsp 2.1 Write 和 Flush 契约](https://github.com/winfsp/winfsp/blob/v2.1/inc/winfsp/winfsp.h#L439-L487)，单文件刷新仅同步这份原文件，不当作全卷刷新、停写或提交。短写或其他本机 I/O 不明后保留原文件，拒绝审阅，不重试或隐去已经生效的局部写入。
- **审阅与退出。** 开始停写后拒绝新的上下文，既有上下文仍能完成最终写入；每个都显式释放后，才可另行确认，同步并按原句柄重新读完整正文得出长度、SHA-256 和是否改变。此阶段不访问网络；不是持久化提交意图，也不是原生 WinFsp 缓存、映射或卷排空的依据。关闭、取消、断线和出错都不会上传或按路径清理失答/已编辑的私有文件。应保留确认时显示的生成路径；当前不能重开认领或自动恢复这份工作文件。

**与真正可提交的编辑盘之间还差什么：** 在受信的 WinFsp 会话中实现并核验虚拟条目的调用者、命名与本机别名、写回缓存/映射、来源/执行策略（含编辑器用无标记临时文件替换原正文）和真实关闭/卸载；将实际排空后的完整正文及相同目标、账号和操作号持久化，并实现只在明确提交时发送、失答后按原号查回执。在这些条件具备前，不能把本页的内存状态当成对外能力。

独立原生资格源例在 `tests/qualification/windows_draft_qualification.py`。需要实际 Windows 11 普通用户、现有固定本机私用 NTFS 合成目录及有效的系统来源标记策略；不改 ACL、不访问真实服务器、不加载 WinFsp、不自动清理合成目录。源例覆盖并发追加、受限写截断、单文件刷新、容量上限及稀疏偏移零填充、缩短再扩展、空正文、未确认/撤销、停接新句柄后的最终写入、半写失败不可审阅及断线保留原文件。本次只检查源码，没有编译、执行或实机验收。

## 单容器整文件准备、原号和冷重开（内部源码）

对已有远程分支头或历史 main 节点，只有原工作文件本次的完整审阅结果确实改变，再单独确认，才生成一个普通全量正文和一份原有 R3 `Plan`。计划只含一个 `save_node`，保留原容器 ID、版本、分支、预期原头、新节点、操作号、正文长度和 SHA-256；历史 main 选中的节点作为新分支父节点，保存和分叉由一次 `save_node` 完成，main 不推进。准备时确定的新分支保存在原计划里，查询或原号重发沿用它。不发送改名，远程原名和生成的本机文件名彼此独立。此步需要额外一份完整正文的本机空间，不预留容量。

在原来选定的私用 NTFS 目录内，先独占创建正文及计划的内部文件，确定各自的真实 FileId。**写正文或发布待决槽前**，先无覆盖发布并同步一份单独的原号凭据；其中的容器、提交号、操作号、计划记录摘要也可以另行保管。正文的来源流先按系统策略写入，同步正文、读回核 SHA 及原实物，再将小计划不可覆盖地改名为该私处、账号、服务器信任配置和容器的待决槽。读回原号不等于已生成完整计划或已向服务器提交。

应用退出后，可用原认证读取器、原目录和明确的容器 ID 核对原号凭据，再用该原号重开已发布计划和完整正文。两次本机操作都不发网络请求；重开会同步原父目录以补确认最后的改名屏障。核对实际目录与各自文件身份、原账号/来源、原节点及标记、全量正文摘要，不寻找其他同名文件、临时文件或后来编辑的工作文件。原号已落盘但缺正式计划时，拒绝收养或重发，请保留现场。原号和正文另存于同一个受本人控制的私处，不防该账号或管理员恶意伪造整个私处；若有另存的原号和完整记录摘要，则可作独立核对。该槽约束该私处，不是跨磁盘的全局锁。

准备模块本身只提供持久本机材料以及供原 R3 上传器使用的、限时的已核只读正文；不发送远端请求、不退役旧槽，第二笔不会覆盖第一笔。单独确认后的传输和本机归档见下文。完整服务器确认、真实 WinFsp 停写、断电持久性和系统盘符都没有验收。独立 `tests/qualification/windows_save_qualification.py` 为同一普通用户条件下的合成源例，覆盖关闭后重开、同字节换件、竞争、原号先行、晚到改名应答及失效的只读游标；未执行。

**只查询原远程回执。** 内部入口可单独确认查询这份原计划：必须由同一目标、原账号的认证供应者证实实际登录名，只请求一次原操作号的 R3 GET。它不需要重新读取草稿或已冻结的大文件，也不能 POST。服务端报告未找到、冲突或结果未知都不会重发；只有完整的容器、操作、分支、父子节点、长度、摘要及返回版本与原票据相符，才将规范回执在本机无覆盖发布、同步和复核。服务器已确认而本机留证失答时，报告原操作号和服务器版本，仅可重新查询同一回执；不会因之前已确认的回执后来查不到就重新开放提交。这不是待决槽退役或 GUI 资格。独立源例另覆盖正文不可用仍查回执、错误目标/摘要、无回执、错账号、重复查询和本机改名应答丢失；未运行。

## 对这一笔保存的单独授权

WindowsOriginalSaveChoice 只读取用户选择的同一私用目录和原操作，交付可审阅的账户、HTTPS 目标、原容器名/ID、分支头、正文长度与哈希及操作 ID。确认这个原决定才允许一次保存。普通目录/元数据连接不获得通用写权限；打开、编辑、正常/强制卸载、检查回执均不会自动提交。

- 同时持有原意图和恢复键，按原文件身份与来源流重新通读独立冻结正文。使用现有 R3 协议：先 GET 原操作；只有明确不存在才允许一次原 POST，发送完整文件（含空文件），沿用原分支、父节点、目标节点、操作 ID 和哈希，不改服务器拼写。POST 前先同步并读回永久的“可能已发”凭证 .zsa。丢回复、冲突、回执不符或网络权限变化均不在后台补发；继续时仍是同一笔。若正文不可用，独立“查原回执”仍不需要正文。
- 只有服务器返回原操作及完整一致的效果，并且本机确实保留该回执，界面才能说已确认。随后先把原意图、再把恢复键用原句柄同目录不替换地归档到按原提交 ID 命名的两个位置，释放活跃槽。归档一半可仅凭原键继续；已归档的旧操作不占用或改写后来出现的新槽。没有删除编辑正文、冻结正文或回执。远端已确认但本机退休步骤未确认时，只重试本地收尾，不重新提交。
- windows_save_qualification.py 包括针对初次发送、响应丢失、相同 ID 重试、凭据撤销、只查状态及两次归档间中断的模拟传输源码。未运行，没有实际请求服务器。

## 桌面使用流程（仅已准入的签名冻结版本）

「存储容器」中用原 HTTPS 账号连接并读取列表。打开容器信息，选择一个分支头或 `main` 的历史节点，点「将所选节点作为本机磁盘打开」。选择现有私有 NTFS 目录、显示给 Windows 程序的文件名和本次文件字节上限。别名只影响这个本机目录挂载点，不回写服务器名称；包含 Windows 保留字或来源流不能完整表示的名字须改用本机别名。默认只有一个受控原文件，可原位编辑；额外勾选后才允许下一节所述的一次同目录经典替换。不支持任意保存为、移动、删除、执行，也不自动启动编辑器。允许本次操作后才验证签名、可能启动已安装的服务、下载原节点并创建私有目录挂载；没有合格组件时按钮禁用。

所选目录须持有已准入的当前用户/SYSTEM/管理员私有授权；推荐普通本机用户目录下已准备的专用子目录，不用同步盘/联接，也不替用户修改权限。打开初期可取消，等待正在执行的本地操作/网络请求在检查点返回。仅在窗口实际显示的已核目录编辑。关闭编辑器和引用该盘的资源管理器窗口，再点「正常停止并核对修改」。原 WinFsp 会话等待已有引用、卸载并核实原挂载点消失，后台再完整核对所写字节；此时没上传。强制结束或外部停止没有可提交证明，保留私有原件，但外部缓存尚未交回的内容可能丢失。原件不是凭路径重新接管或再次提交的权限。

有修改时点「准备完整文件提交」封存原正文和四段原号，仍不访问服务器。核对原服务器/账号、容器、分支、原节点、新节点、完整长度和 SHA-256 后，点「提交完整文件」。网络未知时只查原号；明确不存在原回执后可主动重发同一笔，在同一窗口对同一已确认意图不重复弹确认。若已收到匹配回执但本机记账失败，先只查原回执，再明确完成本地归档，不再重发；同一面板记住已经核实的原回执，即使后来的查询显示不存在或换了对话框也不解锁发送。本地存储失败时不要把程序重启后的缺席当作推翻已取得的服务器回执。

重启后在同一账号下从列表选原容器，用「核对待处理的原提交」选择同一私有目录；可读取活动原号，也可粘贴此前保留的四段原号核对已归档操作。核对原回执不依赖运行中的驱动、原虚拟盘或正文。不要更换到另一目录制造新操作来绕过待决记录。原件位置和四段原号可从窗口文本直接复制，不含口令。当前没有签名验收记录，这段面板源码不是已发布可挂载产品。


### 可选：一次同目录临时文件替换

勾选高级选项时，同意保留原工作文件及**最多一个**新本机临时正文（各自受本次字节上限约束；封存另需一份完整正文）。为避免与 Win32/驱动的大小写对名规则冲突，磁盘内两个名称仅用长度 1–120 的 ASCII 字母、数字及 `._~-`，仍拒绝设备名、尾点及原别名（包括大小写变体）。服务器名称没有这个限制，也不会改变。选择短一些的私有目录，以便包含来源流的普通 Windows 完整路径也能表示。

支持的保存序列很窄：编辑器用 `CREATE_NEW` 创建新的同目录普通临时文件，写入完整内容，`FlushFileBuffers` 后关闭写句柄；全部旧文件、临时文件和来源流句柄都完成原生 Close 后，才允许用仅具所需改名权的原临时文件打开，通过经典 `FileRenameInfo` 同目录覆盖且目的恰好是该次所选别名。没有真正的磁盘替换：两个私有文件的真实 FileID、路径、权限和来源标记都保留，核验并同步过才切换虚拟别名。系统策略要求标记时，临时文件从第一段正文以前就带实际原来源标记，不能改动它。不能用未刷新临时文件、多个临时文件、其他目录/目标、重命名扩展/POSIX 或 `CREATE_ALWAYS` 代替。保留正常的只读 Zone.Identifier，不接受复制外部标记、删除、修改 ACL/EA、备份或运行程序。

编辑器和资源管理器窗口须先关闭，再请求正常停止。原宿主确认打开的是同一驱动卷中实际的新文件编号，且旧临时别名已经不见，再按原流程排空全部引用、卸载并通读选中正文。无法核实临时正文确已在原虚拟卷上成为所选名、原来的挂载/权限/来源证明失效时，不产生可提交审阅；两个私有实物不覆盖、不删除，界面提示保留位置。重新按名打开不是编辑器已经收到成功响应的证明。若编辑器提示保存失败，先核对两处保留文件，不直接提交；不能从崩溃留下的名称取得原编辑或提交权限。明确准备、提交及断线按同号核对不变。

不声称支持任意编辑器的保存。尤其 [ReplaceFileW](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-replacefilew) 还涉及原文件删除、修改另一个 ACL、流/属性合并和备份，某些错误发生在命名或元数据改变之后，不能由同目录覆盖改名回调代替；WPS/Office 备用保存模式、重复临时替换和 `MoveFileExW` 不算已验证。需要依次核对实际编辑器的公开 Windows 操作路线和最终签名包。现有原位模式保持默认，未开放发布。


Qt 6.11.2 的 [QSaveFile](https://github.com/qt/qtbase/blob/v6.11.2/src/corelib/io/qsavefile.cpp#L224-L249) 也不符合上述序列。其 Windows 专用路径 [独占新建时同时请求读、写和 DELETE](https://github.com/qt/qtbase/blob/v6.11.2/src/corelib/io/qtemporaryfile.cpp#L175-L195)，[保持同一写句柄到提交](https://github.com/qt/qtbase/blob/v6.11.2/src/corelib/io/qtemporaryfile.cpp#L388-L417)，用它[执行经典改名](https://github.com/qt/qtbase/blob/v6.11.2/src/corelib/io/qfsfileengine_win.cpp#L400-L425)后才关闭，不是通用 MoveFileEx 路径；还会尝试应用目标权限，失败或取消时删除临时名。不能用打开已有文件直接覆盖当作该项通过。将来的签名包资格须禁用直接写回退，单独证明这个独占句柄的成功刷新/晚到写、权限保持和只对原临时条目的取消，并重新核对提交前后原名、来源流、完整正文及同一操作号。


## 首次提交一个普通本机文件

在已准入的 Windows 客户端登录后选择「提交新的本机文件」，不用先选容器或挂载。选择一个固定本机 NTFS 普通文件和一个应用可验证的现有私有 NTFS 暂存目录。源只有默认数据流；链接、同步占位、加密或带附加流的文件不进入这一流程。服务器文件名单独选择，按原拼写提交，和本机路径无关。

先核对原件和完整摘要。第一次确认只向私有目录封存完整文件和原号，不上传；第二次确认才会查原回执并发送同一原号的全量正文。服务端成功后建立 `main` 首版。发生同名冲突或者结果未知时，不替换原容器，不自动改名或换号。源文件保持不变。

如果关闭窗口，在同一服务器和账号下使用「核对待处理的原提交」，选择原私有目录并输入原容器编号或四段原号。首次提交尚未进入列表时也可核对。已封存的完全相同正文与操作号可按现有原回执规则显式重试；不重新读取初次所选源文件。该入口需要原签名客户端准入，但不使用 WinFsp 服务或驱动。新增普通用户 NTFS 资格源例尚未运行。
