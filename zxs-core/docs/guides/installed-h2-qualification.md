# 已安装客户端：真实 HTTPS/2 与系统信任切换

[仅静态] 这是独立的 [Linux 手动验收作业](../../../.github/workflows/zxs-core-installed-h2.yml)，尚未运行。它不是日常 CI、正式发布或桌面应用验收。只有在另行批准后才从已审查的 main 启动，不能把客机脚本用于个人或生产主机。

## 输入与隔离

- 在 Ubuntu 托管作业里，以 Rust 1.100.0 分别按锁安装历史对照客户端 `1bc616d` 和已更新终端口令依赖的新客户端 `b2958a6`。两个安装来源只含各自的 `zxs-core/`。服务端与 Helper 继续固定到 `5c7815f`，不随客户端换版。
- 签名核验的 Ubuntu 镜像、一次性 ext4 数据盘与只读种子盘组成无网卡 QEMU 客机。运行进程是专用普通账号，真实 ZXS 与诊断前端只监听回环。测试用生成的证书及二进制材料；不会复制个人信任库或文件。
- 仅客机安装合成签发根、加入无关根，再撤掉签发根。独立解码原生证书 DER 集合，先核对两份旧客户端实际登记的信任摘要，再要求集合只增删指定根。宿主不安装包或证书，旧 Workspace 与 FUSE 都不参加。

## 要证明的结果

1. 用两个旧工作区各显式发送一次。前端先读到真实 ZXS 的精确成功回执，再只丢给客户端的那一次应答；两个原操作号不同。再做第二次普通编辑。
2. 加无关根后用新进程分别走回执专用和 Basic 入口，各只查自己的原号。回执入口可另发一次空登录，不能记成资源写入；两次都不重发正文。确认两份旧身份记录不变，较新编辑仍在且待提交，另用 Basic 独立整份读回一个原节点。
3. 无原信任链、证书名字错误、TLS 已建立却没有协商 HTTP/2 时，两种入口都不提示口令、不发授权数据；原地址端口或账号不匹配时不建连接。不是对仍存活旧连接持续监控 CA。
