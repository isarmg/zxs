### 接着需要交付和量测的事

1. 在第三个正式节点之后继续工作修订和更深的规则化增量链，及按显式选择或可验证阈值形成独立 FULL 检查点。工作确认和正式发表仍必须是两项决定。100 GiB 原父仅改 4 KiB 时，须分别量测原父读取、稿/增量验证、收尾及实际新增占用；不能把少写误报为少读。
2. 现行 SYSTEM 登记 inode 的业务决策流有 **8,192 笔、8 MiB 帧总字节**两项独立上限；8 MiB 不含固定登记头，按单帧至多 4,096 字节预留，可能提前拒绝。按 FileId 或 NodeId 读不是常数开销：每次实际当前/历史正文读取都要核对原 SYSTEM 登记、确认下界与决定前缀，同步 SYSTEM 目录；随后核对并持有所选原 FILE/节点，在交付读句柄前同步、复核实际数据卷根。只查询已发布的原操作回执不要求打开数据卷。区间读无需扫描此前整份 RAW，但仍从头流式校验所需的原索引（64 KiB 缓冲）；组合读如分别命中基准与变更还需验证各自原索引。没有跨请求热索引缓存的保证。
3. 后续用小日志与接近两项准入上限的日志分别做冷首读、同 FILE 重复末尾 4 KiB 读、切换 FILE；分开记录系统页缓存、日志解析、可见片段数及 index/BODY 实际字节、原目录/文件同步、FD/内存和并发等待。达到上限的长期方案须有可核验检查点/轮换：保留每个原操作事实、可验证前沿、未完安装/清理和掉电续作，不截尾冒充新池，不增加第二个真相源。此处只是待办，没有运行基准。
4. 其后扩展真实同身份跨卷 MOVE 到无首节点、已确认工作稿和后续放置；把已支持的干净文件软删除/还原进一步扩展到目录整批与授权服务；完整材料核验复用原 FILE 验证器，不将新的诊断命令当作任何正常移动的替代。HTTP/SMB/Web、真实客户端及下表未完成项仍须在产品内逐条交付。
5. 两个 FILE 的容量与等待分别验：在 A 的 100 GB 基准上保留十次各 10 GB 的工作写入，提交和清理间的正文峰值约等于基准 + 全部原工作材料 + 最终贡献的变化（逻辑量示例：互不重叠约 300 GB，反复覆盖同一段约 210 GB；不含头、索引、文件系统开销）。令 A 的已准入读者持续到 INCR 已发表，计量其退稿与原 SYSTEM 槽位的占用时长；分别观察 B 的读取、新建/保存被延后以及 A 收尾后 B 的原请求。不能把这个单槽设计写成吞吐保证。此为待运行验收，不是测得数值。

6. 搬移另验**巨大保留历史、极小当前正文**：使 A 的首 FULL 很大，当前 INCR 将其裁得很小；B 的可用空间只够当前、不够全部保留材料时，原单应在逻辑切换前拒绝。能容纳时按阶段分别记录对完整 FILE 的逻辑核读、实际装入私有目标的字节、源/目的暂时并存与原保留占用时长。同挂载正常流程不抄 payload，首 FULL 仍至少核读三遍：首次签决、改名前再次核原源、安装名重新核实。无中断的普通跨挂载 MOVE 在源侧至少三遍（首次核读、复制、退役前核读）；随后同一源目录改作本票私名，保持全部已核原件和排他锁，只复核实际目录、成员和各件未变，不再整读一遍源。中断并失去句柄后，须从原票重开并核读剩下各件。无中断的普通跨挂载 MOVE 在目标侧至少三遍（匿名读回、签决前已命名私目录、决定后落位前已命名私目录）。同次原子改名保留最后一次核过的原句柄，最终名上的目录、成员、各对象身份与原状态、操作标签和原私名消失仍须核实，不再扫描全部正文。丢失这些句柄的冷重试须完整核读实际目标；这项去重不改变专盘删还。有 INCR 还要验自身和其贡献内容。这些是现行源码的逻辑阶段，不是设备实际读量或实测速度。另有 `custody_handoff.rs` 的独立 FILE 源码用例：原 MOVE 的目标可读，但旧读者或源盘离线阻止原单收尾时，旁边 FILE 的已确认内容可读，新 CREATE/SAVE 暂拒且无回执；接回原盘并核完同一原单后才接受原先两笔请求。未执行。

**当前命名源码边界。** 新池根级 FILE 从原拼写与完整 FileId 派生唯一容器，普通与回收终名一致；真普通目录保留原名字节。用本机 CLI 和原生接口对大小写两份正文/原历史、专盘同名不同 FILE、迟到撞名、受限或掉线的回收卷编写了验收用例，并未执行。子目录 FILE 整链与未来的主分支改名仍单列；改名只影响当前名，不能改写历史创建名。实际 SMB 接入须验证服务配置确实为大小写敏感、错误大写不会误中、目录列表不泄露容器后缀，不能用 CLI 代替。
