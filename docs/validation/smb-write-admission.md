# SMB 写入准入分代与额度授予验证

[ADR 0010](../adr/0010-smb-write-generations-and-extent-grants.md) · [SMB 组件](../components/smb.md)

以下历史部分保留提交作者的交接报告；本项目独立执行的结果见文末。作者报告的环境是：2 vCPU、7 GiB 内存的 Linux 虚拟机，测试临时目录位于 ext4 根文件系统（`TMPDIR=/tmp/zt`）。工具链为本机可用的 Rust 1.97.0（`--ignore-rust-version`），仓库固定的 1.99.0 无法在此环境下载。计数与延迟来自同一进程内的真实核心引擎会话和 spool，不包含 Samba、网络或客户端；不是物理盘、实际 SDK 或吞吐验收。

交接证据范围：下列数字来自提交作者的 Rust 1.97.0 报告。Release `123` 的 `zxs-tasks-4-7.1.zip` 包含提交 `955580ef` 的源码，但不含报告所述 `evidence/` 原始日志及未提交的基线测量补丁。因此这些数字保留为待复核的历史测量，不作为固定工具链、当前集成提交或真实 SMB 性能的采用证明。

## 方法

- 基线：提交 `39fbb997`，测量代码只作为工作树临时补丁加入（未提交），驱动旧 VFS 序列：每次写入 `PrepareWrite` + `pwrite` + `Dirty`。
- 变更后：交接分支，`test/server/unit/smb_rpc/write_generation_tests.rs` 的 `measurement` 模块以 VFS 实际使用的 `WriteSequence` 驱动同一工作负载。测试直接调用 `Session::dispatch`，不经过 socketpair 或 RPC 编解码；下述 RPC 数字是按类型统计的请求次数，不是实测网络往返。
- 两侧均以 `CARGO_PROFILE_TEST_OPT_LEVEL=2` 构建测试二进制，按 `--ignored --exact --test-threads=1` 单独运行。
- 计数：RPC 与预算／恢复记录写入由测试统计（后两者来自仅 `cfg(test)` 的真实持久化包装）；文件／目录同步来自 `strace -f -y -e trace=fsync,fdatasync,getppid`，以测试中的 `getppid` 分隔写入、Flush、Close 阶段，并按路径在运行后是否为目录分类。计时在不挂 `strace` 的独立运行中取得。
- Flush／Close 尾延迟：每轮 40 次「新建 8 MiB 文件（64 KiB 写）→ Flush → 再写 64 KiB → Close」，两侧交替运行三轮以分离环境漂移。

## 写入阶段计数与耗时

| 工作负载 | 版本 | PrepareWrite | Dirty | 预算记录写入 | 恢复记录替换 | 文件／目录同步 | 写入阶段耗时 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 新文件顺序追加 1 GiB，64 KiB 写 | 基线 | 16,384 | 16,384 | 16,384 | 0 | 16,384／16,384 | 14,922 ms |
| | 变更后 | 16,384 | 1 | 35 | 0 | 35／35 | 853 ms |
| 新文件顺序追加 64 MiB，4 KiB 写 | 基线 | 16,384 | 16,384 | 16,384 | 0 | 16,384／16,384 | 14,308 ms |
| | 变更后 | 16,384 | 1 | 17 | 0 | 17／17 | 123 ms |
| 已发布 256 MiB 文件原位覆盖，64 KiB 写 | 基线 | 4,096 | 4,096 | 0 | 2 | 4／8 | 200 ms |
| | 变更后 | 4,096 | 1 | 0 | 2 | 4／8 | 85 ms |

每 GiB（64 KiB 写）：RPC 由 32,768 次降为 16,385 次；预算记录原子替换由 16,384 次降为 35 次；写入阶段文件与目录同步各由 16,384 次降为 35 次；`Dirty` 引起的恢复记录复用核验由 16,384 次降为 1 次。新建文件在 Open 时已是 dirty，因此两侧恢复记录替换均为 0；覆盖工作负载的计数从 Open、预置写入及其 Flush 之后开始，因此不能把这 2 次替换归因于 Open。首次 Dirty 的已提交工作区标脏及后继记录写入需按该阶段分别解释；两侧计数相同。

覆盖写不增长文件，两侧都没有预算增长；但每次写入仍执行 `PrepareWrite` 的空间检查，变更后的差别来自省略同代 `Dirty`。

## Flush 与 Close

Flush 阶段的同步次数在 1 GiB 工作负载两侧相同（文件 175、目录 237）；64 MiB 工作负载为 237 与 243 次目录同步，差异来自引擎元数据按内容哈希分片的目录是否新建（各次运行的随机标识不同），对应路径均位于核心 `metadata/objects`，SMB 写入路径的改动不参与 Flush。

| 轮次 | 版本 | Flush p50／p95／p99 | Close p50／p95／p99 |
| --- | --- | --- | --- |
| 1 | 基线 | 291／357／371 ms | 273／313／339 ms |
| 1 | 变更后 | 283／348／367 ms | 267／327／373 ms |
| 2 | 基线 | 297／372／411 ms | 278／334／378 ms |
| 2 | 变更后 | 291／350／404 ms | 268／306／322 ms |
| 3 | 基线 | 292／374／420 ms | 269／326／343 ms |
| 3 | 变更后 | 302／373／390 ms | 282／331／362 ms |

40 个样本的 p99 即最大值。两侧差异在轮间波动范围内：本改动没有改变 Flush／Close 的工作，也没有观察到尾延迟回退或改善。单次非交替运行曾得到变更后 p50 高约 13% 的结果，交替重测未复现，判定为环境漂移。

- 未执行真实 Samba 客户端、断网、掉电或多客户端互操作验收。


## 独立 GitHub 验收

`fc16eeb3b471d7457814bc5045291f9c3a69639d` 的[合入前 CI](https://github.com/isarmg/zxs/actions/runs/40692653903)与 [main CI](https://github.com/isarmg/zxs/actions/runs/40697284296)均为 17/17 成功。真实 Samba 4.23.0 SDK 的 27 项测试、SMB 协议 46 项测试及核心的撤权、过期、丢回执、后继记录失败与额度恢复回归均已实际执行，不沿用交接环境的抽取类型检查。

[独立测量运行 40701628454](https://github.com/isarmg/zxs/actions/runs/40701628454)固定实际旧服务端 `806c32c9` 和实际新服务端 `fc16eeb3`，使用 Rust 1.99.0、测试优化级别 2、同一 runner／文件系统。旧侧使用旧服务端及其每次 PrepareWrite→pwrite→Dirty 序列，新侧调用实际 `WriteSequence`；不是把旧客户端序列放在新服务端上当基线。

每个负载、每侧均做三次不挂跟踪器的运行，顺序 AB／BA／AB；另外每侧、每负载各做一次独立 strace，共 18 次计时及 6 次跟踪。每次使用新夹具；覆盖负载先写 0x5a 并 Flush，再测量写入 0xa5。所有 24 次都在计时／跟踪阶段之后，以有界缓冲读取并核对全部已发布字节。原始源码补丁、实际测试源码、二进制摘要、逐次计时及六份原始跟踪均保留在运行产物中。

| 工作负载 | PrepareWrite（两侧） | Dirty（旧→新） | 预算增长记录（旧→新） | 写阶段 fsync（旧→新） | 写阶段中位耗时（旧→新，s） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 新文件追加 1 GiB，64 KiB 块 | 16,384 | 16,384→1 | 16,384→35 | 32,768→70 | 10.186728→0.418112 |
| 新文件追加 64 MiB，4 KiB 块 | 16,384 | 16,384→1 | 16,384→17 | 32,768→34 | 10.027379→0.161883 |
| 覆盖已发布的 256 MiB，64 KiB 块 | 4,096 | 4,096→1 | 0→0 | 12→12 | 0.214657→0.059492 |

写阶段没有 fdatasync；三种负载的恢复记录替换次数两侧分别均为 0、0、2。Flush 同步总数分别为 413→413、413→401、347→353，其中每种负载两侧各有 13 次 fdatasync；这些实际总数不支持“Flush 同步一定减少”的结论。随后测的是已 Flush 的干净 Close，同步总数均为 0，不是 dirty Close 或尾延迟测量。只有三次时间样本，不报告 p95／p99 稳定性。

同步计数覆盖标记之间的全部被跟踪线程，逐阶段、路径、线程及 deleted 标记保存；未用事后路径是否存在来猜文件／目录类别。首次运行因解析器未支持匿名临时文件的 `fd</path>(deleted)` 表示而失败。修订仅更改验证工具：保留该注解，按驱动创建的唯一调用 TMPDIR 判断归属，再完整重跑全部 24 次；未跳过失败路径或修改产品逻辑。第二次运行的 140 项证据摘要及六份原始跟踪均经独立复核，ZIP SHA-256 为 `6de0436c76e3aade4e21560fcf38de62ec9448ba45c1c6539884f6c692823981`。

**范围限制：**这是进程内 `Session::dispatch` 加真实引擎／spool 的版本对比，不包含 Samba 客户端、Unix socket、编解码或网络吞吐。Runner 的 ext4 挂载包含 `nobarrier,data=writeback,journal_async_commit`，不能作为物理盘耐久性、掉电或生产挂载策略的验收。两版本还包含其它源码差异，因此请求／预算／同步次数能确认目标机制，不能把全部墙钟差异严格归因于单一改动。
