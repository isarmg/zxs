# 文件容器备份镜像的完整条目预算

## 问题与修复范围

`backup_entities::Image` 和 `backup_ordinary::Image` 都先计入文件路径，再补齐缺失父目录，最后插入文件；ordinary 还以同样顺序插入 locator。原检查只观察补父目录前的条目数，父目录耗尽最后名额后，文件或 locator 仍会插入，产生超过 100,000 项的计划。后续库存检查使用完整数量，预备图还另计固定 manifest，可能在安装后才拒绝这个计划。

本片保留初始路径、字节和条目检查，统一各自镜像的条目计数入口，并在父目录创建后、文件或 locator 插入前重新检查。该检查针对已改变的资源计数，不重复证明仍有效的状态。恰好达到上限的完整计划仍可接受，已有父目录不重复占名额。失败的私有计划由原调用方丢弃；没有新增物理写入、回滚或恢复机制。

未改变公开 API、磁盘格式、原请求摘要、永久收据、名称生成、复制独立性、同步顺序、系统／盘根／容器数据库的范围或授权。每次文件／locator 增加一次常数时间计数；集合遍历和祖先规划的复杂度不变，没有性能测量结论。

## 定向验证

新增六个真实规划器回归，直接使用生产的 100,000 项限额，不加测试专用预算开关：

- 预备实体图的两个缺失父目录填满预算后，正文条目返回 `RESOURCE_LIMIT`；恰好容纳父目录及正文成功；已有父目录不额外计数。
- 普通容器图分别验证文件与 locator 的缺失父目录越界；恰好容纳两级父目录、文件与 locator 成功，再追加条目拒绝。

`backup-entity-entry-budget` 定向组还选择原 ordinary 存储／locator 行为模块、完整原生 Backup 切换及后继冷重放的一项集成回归，以及独立产品库编译。单元测试构建仍沿用现有 dev-dependency 注入特性；产品编译不是无注入运行测试。

本片未本地编译或运行测试。GitHub 的准确提交选择、编译与执行结果是验收依据；此文只登记范围，不代表 CI 已通过。规划边界夹具不在磁盘安装十万项，不等同于磁盘满、真实掉电、真实盘或全部成员恢复验收。

## 三范围与多级布局的当前边界

当前[数据模型 §7.3](../07-data-model.md#s07-03)把三份数据库定义为系统全局、盘根本盘、容器／独立仓库本对象三种不同范围。它明确保留原发布证明，未建立完整代际和三范围整体恢复／迁移闭环；本片不把三份字节相同或多数票视为权威选择。

[磁盘身份与保留区布局](../adr/disk-names-and-retained-layout.md)仍标明运行时接线未完成。递归备份目前冻结配置根 basename，再以直接来源链生成多级路径；尚缺独立持久名称登记、名称代际和覆盖全部下级的改名事务。`common-data`／`deleted-data`／`zxs-data` 及“可读盘名＋完整 UUID”是目标布局，本次没有通过替换路径字符串激活它，也没有改写历史 capture、收据或已存在实体。
