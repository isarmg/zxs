# 常数时间原语的维护要求

## 原因与范围

活动来源不得使用 [RUSTSEC-2026-0385](https://github.com/RustSec/advisory-db/blob/main/crates/ctutils/RUSTSEC-2026-0385.md) 所列受影响版本。当前采用官方 `ctutils 0.4.4` 修复，不忽略公告、不按目标平台排除审计，也不只修改版本号。

公告涉及两类编译后常数时间性质：

- `Choice::to_*_mask` 的旧实现可能生成依赖输入的分支。上游 [PR 1567](https://github.com/RustCrypto/utils/pull/1567) 改为经 `to_u8()` 的优化屏障生成掩码，并增加机器码验证。
- `u128` 比较在 32 位目标上可能生成分支。上游 [PR 1568](https://github.com/RustCrypto/utils/pull/1568) 为相关比较增加分半处理，并调整 `CtLt`／`CtGt` 路径。这一特定条件不能直接描述为 Linux amd64 的 `u128` 缺陷；掩码问题则不限于此条件。

秘密相关分支可能形成侧信道；这不等于已证实 ZXS 的某个接口能被利用，也不代表用户秘密已泄露。[官方 0.4.4 发布 PR](https://github.com/RustCrypto/utils/pull/1569) 将上述两项列为安全修复，公告标记 `>= 0.4.4` 为已修复版本。

## 本项目依赖边界

Linux x86_64 依赖关系中：`authentication → hmac → cryptographic-core` 的 `mac` 功能引入 `ctutils`，并进入服务端和辅助工具的依赖闭包。`cryptographic-core` 同时被 SHA-2、Blake2 等组件共享；依赖图存在不证明每个消费者调用了受影响原语。

本项目认证代码使用 HMAC-SHA256 派生 CSRF token；共享 MAC 实现包含 `ctutils::CtEq`。未建立秘密相关掩码或 `u128` 比较在产品请求路径中可利用的证明，不将依赖告警扩大成已证实攻击。但既然活动来源受公告覆盖，仍升级完整组件，而非用未发现调用来豁免。

单独以 `-p web-app --target wasm32-unknown-unknown` 检查时，`ctutils` 不在该浏览器产品的依赖图内。wasm32 是评估 32 位实现及跨目标兼容性的相关目标，但不能据此声称当前 Web 产物包含该依赖，或把针对组件的 wasm32 编译检查当成浏览器侧信道验证。

## 精确来源与保留要求

- 官方归档：[ctutils-0.4.4.crate](https://static.crates.io/crates/ctutils/ctutils-0.4.4.crate)。
- SHA-256：`12218662ccac37d9714f2191252553d67585b97df8c839cbe49e0bde278dc865`，与 crates.io 稀疏索引对应版本记录核对。
- 归档 VCS 身份：[`a993c0ba50db6510d8db15a6219572de65115438`](https://github.com/RustCrypto/utils/commit/a993c0ba50db6510d8db15a6219572de65115438)，上游路径 `ctutils`。

更新须导入实际官方修复源码，并保留本项目路径依赖及根测试布局。新来源收据、许可证和原始发布元数据追加保存；旧 `0.4.3` 原始来源与历史文件不得覆写。测试外置的路径适配须单独记录，不能伪称修改后的全部文件仍为上游原字节。显式升级关系及来源校验应证明活动身份确实已被新实现替换。

分组目录之后的上游升级另有窄范围来源适配：保留原布局固定哈希对应的 `origins.json` 原字节快照，只允许明确升级链对应的新增来源。首个退役前驱的源文件清单和外置测试收据须与固定布局证据一致；新源码读取受当前清单约束。该适配不重设旧布局收据、不放宽无关历史，也不支持未经证明的共享组件升级。

## 验证要求与结论边界

新候选须重新执行来源治理、锁文件与离线闭包检查、组件和认证回归、严格质量检查、在线安全扫描，以及完整发行演练。记录最终候选提交和运行结论，不能复用旧提交产物作为新版本安全证据。编译和功能测试通过不等于常数时间机器码证明；上游 BINSEC／`cargo checkct` 的验证也不等于已验证本项目全部编译选项、目标或运行环境。

实际验证结果以对应候选工作流为准，旧扫描不代替当前检查。
