## 补上的真实缺口

文件库、目录库、盘根 current 和盘根 history 的闭集解码器原先校验固定 schema、作用域、规范行、预算和逻辑摘要。逻辑摘要只能覆盖查询实际返回的行。SQLite 索引损坏时，有序索引遍历可能遗漏物理表中仍保留的行，并恰好与旧摘要相等；此时不能把读到的子集认证为完整救援材料，也不能据此覆盖旧库。

四个解码器现于原逻辑校验成功之后、返回已验证快照之前，共用一次 `integrity_check(1)`。它检查页布局、索引与表的对应等物理不变量；不用省略索引对应检查的 `quick_check`。这不是第二次全量 typed 解码，也不从未检查的物理残留中猜测业务记录。

适用文件：

- `.zxs-file.sqlite`：本文件自己的节点、分支和保留审计。
- `.zxs-directory.sqlite`：本目录仓库内部组成和历史。
- `.zxs-disk.sqlite`：本盘当前版本、路径及目录清单。
- `.zxs-disk-history.sqlite`：本盘实际保留的清单变化及覆盖边界。

检查位于既有完整解码边界，既覆盖离线 inspect/export/rebuild，也覆盖使用这些解码器的普通准入与重建前保全。没有新增后台任务、另一个源选择器或备份 writer；没有改变 SQLite 格式、业务摘要、持久字段或三范围职责。SYSTEM 的其它 SQLite 不由本片扩展覆盖。

## 读取、错误与资源约束

调用者已经在独占的只读内存连接中完成闭集 schema、规范行与摘要校验，且该连接不带其它进度处理器。物理检查复用它，不再复制镜像，不打开文件路径，不创建 sidecar、暂存文件或修复库，不调用持久写入及同步。完成或失败后清除本次进度处理器，再由原调用者关闭连接；检查错误与清理错误同时存在时保留两者。

仅恰好一条 `ok` 结果表示通过。SQLite 诊断最多取两行，每行最多 512 字符；非 `ok` 或 SQLite 执行错误返回明确 `ContainerLayoutInvalid`，不当作缺失或空库。执行每 1,000 个 SQLite VM 操作检查一次预算，最多允许 10,000 次成功回调；超出时中断并以 `ResourceLimit` 保留底层错误。这个约千万步的预算不是墙钟超时、全部 SQLite 内部 CPU 指令或进程 RSS 的硬上限。

原 16 MiB 对象镜像／32 MiB 盘根镜像、行数及记录字节预算不放宽。完整性扫描新增读内存与索引比较工作，成本取决于页数及索引查找，通常为 O(页数 + 行数 × log 行数)。它位于已有全量解码上，仍会增加普通完整校验调用的 CPU 时间，不能宣称零开销；没有新增文件 I/O 或 fsync。最大合法材料的耗时及预算余量仍需专门规模验收。

## 失败时保持原材料

物理损坏时停止返回材料，不自动修复索引、不把查询可见子集重编码覆盖原库。普通目录重建同样先拒绝有未知保留字节的旧库；源文件和逻辑发布序号不因检查失败改变。

盘根救援仍遵从显式范围：选择 `history` 不访问未选择的 current，选择 `current` 也不访问未选择的 history；选择 `both` 则两者均须通过。未检查不是已确认缺失，更不是另一个库已完好。

通过物理检查仍只证明这份 SQLite 的内部表示。全部内容被自洽改写的镜像可能通过，它不认证 publication、正文、最新状态、权限或跨范围权威。不能据此激活外来盘、复活退役节点或替代完整三范围恢复。
